Piece one. Token bucket rate limiter.

Problem. Allow about N requests per client per window, with burst. Classic: capacity C tokens, refill rate R tokens per second. Each request costs one token. If tokens remain, allow and decrement. Else reject with a clear rate limit error.

Thinking. Clarify: per client_id or global? Burst size equals capacity? Fairness? Clock: use monotonic time, not wall clock that jumps. Naive: log timestamps per client, prune older than sixty seconds, count — correct, O of requests in window memory. Improve: token bucket O of one state per client — tokens float, last refill timestamp.

Refill math. On each request, elapsed equals now minus last refill. Add elapsed times rate to tokens, cap at capacity. Set last refill to now. If tokens at least one, minus one, allow. Else reject.

Trap. Forgetting cap after refill — tokens grow forever. Using wall clock that steps backward. Silent drop without error type. Shared bucket across clients by mistake.

Pseudocode. Class with capacity, rate, tokens, last refill. Method allow: now equals monotonic time. Tokens equals min of capacity and tokens plus elapsed times rate. Last equals now. If tokens greater than or equal to one: tokens minus one, return true. Else return false.

Why. Constraint: bursty traffic, O of one check, per client. Rejected pure fixed window that allows double burst at boundaries if they want smoother control — mention sliding window as alternative. Token bucket buys burst up to capacity and sustained rate R. Cost: float tokens and clock dependency.

Piece two. Circuit breaker.

Problem. Protect calls to a downstream bank or KYC or FX provider. States: closed means healthy, calls pass; open means fail fast without calling; half open means allow a probe.

Thinking. Clarify failure threshold, open timeout, what counts as failure. Naive: always call downstream — cascades when partner is down. Improve: state machine with counts.

Transitions. Closed: on success reset failure count; on failure increment; if count hits threshold go open and stamp open time. Open: if now minus open time less than timeout, reject immediately; else go half open. Half open: one probe — success goes closed, failure goes open again.

Trap. Reversing open and closed meaning. No half open — flap forever or stay open. Counting successes wrong in half open. Not failing fast in open — still tying up threads.

Pseudocode. Enum state closed open half open. Fields failure count, threshold, timeout, last failure time. Method call wrapper: if open and still in timeout, raise fail fast. If open and timeout expired, state half open. Try execute function. On success: state closed, failures zero. On failure: failures plus one, last failure time now; if half open or failures at threshold, state open. Rethrow.

Why. Constraint: partner outage must not exhaust our workers. Rejected infinite retries without shed load. Circuit breaker buys fail fast and recovery probe. Cost: extra state and risk of false open if threshold too low.

Piece three. Idempotency key store.

Problem. Payment style API: client sends idempotency key. Same key plus same body returns the same result without double charging. Same key different body is a client error.

Thinking. Clarify key scope — usually merchant and key. TTL for stored records. In-flight concurrent same key — lock or mark processing. Naive: no store, every retry double applies. Improve: map key to record of request hash, response, status.

Flow. Lookup key. If missing, process, store hash and response, return. If present and hash matches, return stored response. If present and hash differs, return four twenty-two style unprocessable. If in progress, return conflict or wait per policy.

Trap. Key only without body hash — different amount same key silently wrong. No TTL — infinite growth. Not storing failure responses consistently. Race two concurrent first requests without locking.

Pseudocode. Store map key to record. On request: existing equals store get key. If existing and body hash differs, error. If existing and complete, return cached response. Else process business logic, store record with hash and response, return.

Why. Constraint: at-least-once client retries must not double-apply money. Rejected "always process" and rejected "ignore key." Idempotency store buys safe retries. Cost: storage, TTL ops, concurrency control.

Piece four. Outbox one-liner.

Problem. Dual-write gap: write payment row then publish Kafka — one can succeed and the other fail. Outbox: in the same database transaction, write domain row and outbox event row. After commit, a publisher reads outbox and publishes, then marks sent. Naive dual write is the dead-end. Why outbox: atomic durable intent to publish; at-least-once publish with consumer idempotency.

You need not implement full outbox on a sixty minute LC screen; you need the speech and maybe a tiny interface. If they ask code, model outbox table insert beside the domain insert in one transaction commit.

Combined trap clinic. Mixing rate limit and circuit breaker — different layers; gateway rate limits clients, breaker protects dependencies. Using float for money in idempotent payment body hash examples — prefer minor units. Silent coding design problems — always narrate state transitions.

Edges across designs. Capacity one bucket. Breaker threshold one. Empty idempotency key rejected. Outbox publish crash before mark — retry publish, consumer must be idempotent.

Pseudocode portfolio — the portable close.

Token bucket allow with refill cap and monotonic clock.

Circuit breaker: closed open half open with fail fast and probe.

Idempotency: key to hash and response, conflict on hash mismatch.

Outbox: same transaction domain plus outbox row; publish after commit.
