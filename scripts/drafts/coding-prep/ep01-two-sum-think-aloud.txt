Here are the clarifiers I always ask.

Is there always exactly one solution? A lot of LeetCode statements guarantee that. If yes, I don't need a fancy not-found path. If not, I need a defined contract.

Can I use the same element twice? That is, is index i equal to j allowed? Almost never. So I must not pair a number with itself unless the problem says so.

Are negatives and zeros allowed? Yes usually. That means I shouldn't assume all positive.

Duplicates? Like three threes. That matters for the map approach — I need different indices.

Can I mutate the array? If I sort, I lose original indices unless I track them. So if indices are required, hashing is cleaner than sorting.

Assumptions for this walkthrough: exactly one solution, distinct indices, integers can be negative, indices required.

Naive approach — say it first, even if you already know the optimal.

For i from zero to n minus one, for j from i plus one to n minus one, if nums i plus nums j equals target, return i and j.

Time O of n squared. Space O of one extra.

Is that acceptable? For n equals ten to the five, no. For n equals a hundred, maybe. In interviews I still state it, because it proves I can get a correct answer under pressure. Then I improve.

Dead-end I almost take under stress. Someone says: sort the array, then two pointers from both ends. That finds values that sum to target, but the problem asks for indices. If I sort in place, original indices are gone unless I wrap each value with its index first. On a real screen I say that trade-off out loud: sorting works if values only; for classic Two Sum with indices, I switch to a map.

Better idea. I want, for each number x, to know whether I've already seen target minus x.

That's a hash map from value to index.

One pass. For each index i with value x, let complement equal target minus x. If complement is in the map, return the stored index and i. Otherwise store x mapped to i and continue.

Why lookup before insert? Because if I insert first, a single element that is half the target could match itself. Example: nums equals three, three. Target six. If I insert three at index zero, then at index zero I look for three and find myself. Wrong. So: look for complement first, then insert. With two threes, first three stores at zero. Second three looks for three, finds zero, returns zero and one. Correct.

Concrete example. nums equals two, seven, eleven, fifteen. Target nine.

Start with empty map.

i equals zero, value two. Complement is seven. Not in map. Store two to zero. Map is two maps to zero.

i equals one, value seven. Complement is two. Two is in the map at index zero. Return zero and one.

Done. I don't even need eleven and fifteen.

Second example for edges. nums equals three, three. Target six.

i equals zero, value three. Complement three not in map. Store three to zero.

i equals one, value three. Complement three is in map at zero. Return zero and one.

Third case people mess up. Suppose target is six and I only have one three. No second three. Map never finds a pair. Under "exactly one solution" this shouldn't happen. In production code I'd return a defined empty result.

In my head, the code looks like this. Full words, no single-letter soup.

Create an empty map called value to index.

For index i, value in enumerate nums: complement equals target minus value. If complement is in value to index, return value to index of complement, and i. Then set value to index of value equal to i.

That's the whole algorithm. If your language needs an explicit not-found return, add it after the loop.

Time: O of n expected with a hash map. Space: O of n auxiliary.

Trade-off again: if the interviewer only wants the values, not indices, and the array may be sorted, I can sort in O of n log n and use two pointers from both ends. That uses less extra space if I sort in place, but sorting destroys original indices unless I keep pairs of value and original index. For classic Two Sum with indices, map wins.

Edges checklist, speak it. Empty array. Single element. All zeros with target zero if same index forbidden. Negatives. Duplicates. Guaranteed solution removed.
